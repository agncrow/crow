# redis

The RESP door of Magpie: a Redis client's SET and GET a put and a read of the image, INCR and MGET and DEL over a log keyed by the key, a stream a log of its own with XADD and XREAD by position — RESP2 as redis-cli and every client write it, served from one loop.


Import with `use redis`. The RESP door of Magpie, written in Crow on the sys layer and `use magpie`: a Redis client connects to the port and speaks RESP2 as redis-cli and every client library write it — a request an array of bulk strings, a reply a simple string, a bulk string, an int, an array or an error — and the door answers from Magpie. The keys and values live in one log under the door's root, `<root>/_kv`, keyed by `key`, a row per write with a `dead` flag for a deleted key: a GET a read of the sequencer's image in memory, a SET a put, flushed by the sequencer's thread. A stream is a log of its own, `<root>/<name>`: XADD a put, the entry's id its position (`12-0`), XRANGE and XREAD reads by position.

**Design Note: a door per protocol, not a protocol of our own.** Considered: Magpie's own wire protocol with a client library per language (rejected: every language already has a Redis client, a Kafka client and an HTTP client). Decided: the Kafka door's pattern applied again — a protocol written in Crow over the sys listener, each command a verb of the log — so the clients of three products reach one store; expiry (EXPIRE, TTL) waits on the expiry column, and the commands over Redis's structures (lists, sets, sorted sets) are not here: a sorted set is `latest` sorted, a list is the log.
