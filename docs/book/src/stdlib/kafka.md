# kafka

The Kafka door of the lake: a topic a log, a producer's records appended as a batch, a consumer's fetch a read from its offset, groups and their commits two logs of their own — the protocol a 0.10.1 broker speaks, served from one loop.


Import with `use kafka`. The Kafka door of the lake, written in Crow on the sys layer and `use lake`: a topic is a log under the door's root (`<root>/<topic>`, one partition, its positions the offsets), a producer's records are appended as one batch (`at`, `key`, `value`, and the producer's own `offset` as it wrote it; the log's position is the offset a consumer sees), a consumer's fetch is `since` from its offset, and a group's memberships and committed offsets are two logs of the door's own (`<root>/_groups`, `<root>/_offsets`). The protocol is the one a 0.10.1 broker speaks — ApiVersions says so, and every client then writes and reads legacy message sets of magic 1 — framed, parsed and answered in Crow; the per-byte half, a message set to a frame and back with its checksums, is the kernel's (sys, `records`, `records_of`). The door serves every connection from one loop, each polled in turn for its next request, so both modes run it the same way.

Held to the pure-Python client (tests/kafka.rs, kafka-python 3.0.11): a producer's three records land at offsets 0 to 2, a consumer group reads them from the start with their keys, commits, and a second consumer of the group takes up after the commit, in both modes. A consumer group of several members is served as a broker serves one: a new member opens the next generation and carries the others forward, each hears of the rebalance at its heartbeat (`REBALANCE_IN_PROGRESS`) and joins again, the answer lists every member with its metadata, the earliest member present leads and assigns through SyncGroup, a follower that syncs before the leader has assigned is told to sync again, and a member that leaves moves the rest to the next generation. A fetch with nothing to answer waits in the door's loop up to the client's `max_wait_ms`, answered when rows arrive, so a consumer polls without spinning. Compressed message sets are read: gzip, and snappy in xerial's framing or raw (lz4 is refused, naming the codec); a payload that is no UTF-8 text is refused, since a topic's rows are text.

**Design Note: the oldest protocol every client speaks.** Considered: the current protocol (record batches of magic 2 — varints, CRC-32C, headers, compression — and flexible request versions with tagged fields) (rejected for the first door: a client reads the broker's ApiVersions and speaks what it says, so a door that says 0.10.1 is spoken to in legacy message sets, a fixed layout with one checksum, by every client written since — the pure-Python client, librdkafka's, the Java one — and the record kernel is a page where the current format is a chapter; the current format is the door's next step, behind the same `records` rows). Considered: a thread per connection (rejected: the interpreter runs `later` inline, so a door that spawned would serve one client at a time interpreted and many compiled — the two modes must run the same way — and a Kafka client opens several connections at once: one for metadata, one per broker, one for its group's coordinator; one loop polling each connection, waiting five milliseconds at a time, serves them all the same way in both modes). A topic's one partition is the lake's one log; partitions would be logs under the topic, and are not made until a client asks for them.
