# sys

The standard library's own layer: bytes, files, and a connection to a host, for the modules written in Crow and the packages that need a kernel's speed — meant for library code, which any program or package may import.


**Two operations over functions, for the standard modules** (section 7 of docs/extending-crow.md): `describe[f]` answers a function's description as a parsed value — `name`, `doc` (the comment written above it), `params` (each `name`, `takes` — the word errors use for its kind: `an int`, `a number`, `text`, `a bool`, `a list of ints`, … — and `default`, or `null`), `answers` — and `apply[f, args]` calls the function with its arguments read by name from a parsed value or a map, each by the parameter's kind, and answers the value encoded as text: an argument missing or of another kind is an error value of kind `call`, the function's own failure its value. Each takes a function written, or one of a group (a list literal of functions: Specialization), and is lowered to what inference knows — a dispatch the compiler writes over every function the value can be — so both modes agree by construction. A parameter nothing types is refused with the fix (`weather's parameter 'city' is typed by nothing — read it in the body, or call weather[…] once with a value of its kind`); one handed a parsed value, or typed by nothing, takes what the body reads it as, or its default's kind; one of a kind no name can hand (a frame, a function, a handle) is refused where it is applied. A program outside the standard library does not call them (sys is the library's own).

**Design Note: functions as values for native rows, described and called by name.** Considered: a tool written by hand beside the function (rejected in llm's note); a list of function values of one signature only, each a function pointer compiled (rejected: a value's name cannot be recovered compiled, so `describe` could not say what it was handed, and tools of several signatures — the common case — could not share a list); a new expression that chooses by a name at run time (rejected: a dispatch written once by the compiler over the members, which it knows, is the same thing without a construct). Decided (2026-10-19): a native row declares the function it takes with its signature (`Kind::FnOf`: `any`'s predicate over the walked items, `later`'s deferred work handed the rest, `stream`'s feed handed `put`, `route`'s handler the request, `transact`'s body the connection, a chart's `seek` an event), and inference, the checks, the width pass and the classification read the one declaration; a list literal of functions is a group, held by name; `describe` and `apply` are sys's, lowered to a dispatch the compiler writes.

Import with `use sys` — **meant for library code**: the layer the standard library's own Crow-written modules stand on, and a package that needs a kernel's speed — bytes, files, and a connection to a host read and written as bytes. A program serves with `serve[…]`, reads with `request[…]`, `read[…]` and `socket[…]`, and connects with `connect[…]`, which are built on this layer (design rule 20); keeping `sys` to library code is a suggestion, not a rule, and any program or package may import it (Vijay, 2026-10-29).

A stream is one connection however many values hold it, as a socket is; `type[s]` is `stream`. A socket is a stream and what it read past the last message — a WebSocket's connection after its handshake, or a process started under the program (`start`), whose output comes line by line; `type[p]` is `socket`, and it shows as `<socket /bin/cat>`. Every function works identically in both modes (`crow_runtime::sys`). The HTTP protocol is written on this layer, in `src/modules/sys.co`, as functions of `sys` itself: a URL taken apart, a connection opened plain or behind TLS, the request line, headers and body sent, the answer's head read to its blank line and its body by its length, by its chunks, or until the server closes (`exchange`), redirects followed and a reader's options applied (`fetch`), an S3 object signed as AWS's Signature Version 4 says and read or written by path at an endpoint (`fetch`, `put`). On the protocol stand the HTTP client — `request` (Requests), in `src/modules/core.co` — and every reader of a URL or an S3 object: `read` and `write` (core.co), `use io`'s `csv` and `lines` (io.co), `use frame`'s `load` and `save` (frame.co) and `use math`'s `load` (math.co), each a few lines over the layer's parsers (`csv_rows`, `frame_of_csv`, `tensor_of_frame`). A program never sees the layer: it sees `request` and `read`, effects the session layer holds, whose rows in the builtin table are the contracts the Crow bodies keep until effects are declared on the layer's own rows (math.nn, Design Note "a module written in Crow declares its functions by writing them"; docs/extending-crow.md, phase 3).

**Design Note: the standard library's layer.** Considered: writing the standard library's modules in Rust only, as they were (rejected: a module both backends share is a bug both share, which no parity or fuzz run can see; the week of 2026-10-03 found eleven bugs where the two backends differ and none in the kernels they share, because nothing can look there); giving every program bytes, sockets and threads (rejected: a program would gain the bug classes the language exists to exclude — data races, half-read buffers, protocol state spread over user code — and a second way to serve and connect beside `serve` and `connect`). Decided (Vijay, 2026-10-03): one `sys` module, the smallest native layer the rest of the library can be written on, importable by the compiler's own modules alone; a program sees one way, and every module written on `sys` is compiled and run twice, fuzzed, and takes laws. Then (Vijay, 2026-10-29): importable by any program or package — keeping it to the standard library is a suggestion, not a rule — so a package that needs bytes and files at a kernel's speed is written on it outside the standard library, and the reference still teaches `serve` and `connect` as a program's one way to serve and connect.
