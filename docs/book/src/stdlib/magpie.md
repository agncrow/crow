# magpie

The log as a directory of batch files: each commit one file written once, holding its rows' positions, sorted by key, with the statistics a reader prunes by; appends, reads from a position, the latest version of each key, lookups, and a sequencer that refuses a stale read.


Import with `use magpie`. The log as a directory of batch files, written in Crow on the sys layer (design rule 20): each commit is one file, written once by the kernel (sys, `batch_write`) — a frame given a position per row in a column `_pos`, its rows sorted by the key columns, in row groups of a few megabytes, and in the file's index the statistics a reader prunes by per column per group (min, max, the missing and distinct counts and a bloom filter, a filter over the words of each text column indexed), read on demand: a reader of two columns of a thousand reads two columns' index and two columns' chunks. The file is Magpie's own format (sys, `batch_write`; docs/magpie-design.md, phase 2), no library's. Every write of a process goes through its sequencer (`put`, `batch`, `commit`): the rows are visible to the process at once and durable at the flush, and `latest` of one key (`equal`) reads its newest row from the image in memory. One file is at once the log entry (positions), the level-0 segment (sorted, with statistics) and the search index (word filters, and the counts a search's scoring reads). The numbering, the sequencer, the reads, the search and the catalog's state are the module's; a log is a directory path, a snapshot a position.

```
use magpie
use frame

made = mkdir['orders']
first = batch['orders', frame.new[id = [1, 2], qty = [10, 20]], by = ['id']]
log[first]                                   --- 0
second = batch['orders', frame.new[id = [2, 3], qty = [25, 30]], by = ['id']]
log[head['orders']]                          --- 3
log[latest['orders'].qty]            --- [10, 25, 30]
log[lookup['orders', ['id'], ['2']]._pos]   --- [1, 2]
stale = commit['orders', frame.new[id = [2], qty = [26]], seen = 1, columns = ['id'], equal = ['2']]
log[stale.reason]                            --- conflict: id = 2 was written at position 2, after snapshot 1
log[merge['orders']]            --- orders/S000000000001.segment
log[latest['orders'].qty]            --- [10, 25, 30]
```

**Nodes and shards.** A second node is a follower of the log (`share`, `follow`): it holds the same files and the leader's manifest, reads them with the same verbs, and serves what the leader serves; the leader is the one process that writes, and a follower promoted by the operator writes from the head it holds — there is no election, since every file a follower lacks is one `follow` fetches, and a leader that writes nothing more is followed to its last file. A table too large for one node is split into logs by a key (`orders_a`, `orders_b`, a directory each, on a node each), and a query runs the same verbs on each and stacks the answers: `frame.stack[latest['orders_a', k], latest['orders_b', k]]`, or a reduction over each log's part. Nothing in the module knows a shard: the placement is the program's, written where the logs are named.

### Encode (`use magpie.encode`)

A column chunk, in Crow: the cells of one column over one row group as a Magpie file writes them, encoded by the column's kind and passed through the codec where that shrinks them, the kernel's bytes byte for byte. A chunk is an encoding byte, a flags byte (a presence bitmap follows; the payload went through the codec), the row count, the raw and the stored payload's lengths, the bitmap where cells are missing, then the payload: ints by frame of reference or by delta, whichever is smaller; floats as their bits, 32 of them where the column is narrow; text as bit-packed lengths and bytes, or as a dictionary and codes where the distinct values are at most half the cells; bools as a bitmap; moments as milliseconds and offsets; vectors as the rows' floats laid flat. The column's cells come and go as the vectors they are held in, never one at a time.

### Bloom (`use magpie.bloom`)

A bloom filter over byte strings, in Crow: `k` hashes into `m` bits, the two hashes FNV-1a and a mix of it (double hashing: the i-th position is h1 + i·h2 modulo m), so a filter written today reads the same tomorrow; eight bits per item and six hashes, about 2% false positives; the kernel's bits bit for bit. What a file keeps per column chunk over its distinct values, and per indexed text column over its tokens.

### Merge (`use magpie.merge`)

The streaming merge, in Crow — batches and segments, each sorted by the log's keys then position, folded into segments of bounded size, the kernel's segments and manifest byte for byte. What is held is one row group per input and the rows not yet decided, in the merged order: a frame sort of what is held, stable and adaptive to the sorted runs it is handed. Each round decides every row at or before the least, in that order, of the last rows the inputs with groups left have loaded — no row an input has not loaded can come before it — and loads the next group of the input that row came from. Where the log keeps one version per key, the run of the bound's key is held back until a row of another key follows it, and a run decided keeps its last row, the newest. A group of the output is cut where its rows' bytes reach the group's size as the kernel counts them (8 an int or a float, 10 a moment, 1 a bool, a text's bytes and 4, 8 per number of a vector), a segment where its file reaches the segment's size. **Design Note: one file per commit, and the module over it.** Considered: a write-ahead log of row-shaped entries, a memtable flushed to sorted segments and postings built beside them — three writes per row, three structures (rejected: every durable database pays them, and no reader of this log needs them apart: a batch file sorted by key with statistics in its head is the segment a scan prunes, the index a search prefilters, and the entry a consumer reads by position, so the row is written once at commit and again only when files are merged). Considered, for the kernel's reach: the sequencer in the runtime under a lock (rejected: the validation is policy, which is Crow's; the kernel claims a number atomically — a file linked into place only where none exists — and the Crow module validates every file before the number it claims, so a slip is a retry, not a hole). Considered, for the name: `log` (taken by the console), `store` (sys's `store` row), `journal` (rejected: long), `lake` (the first name, rejected 2026-10-26: the industry's word for raw files other engines query, where this store holds its state and runs its own engines), `keep` (a web option), `hold` (the spec's verb on every page), `ledger` (the log alone, not the engines over it), `corvid` (heard as covid) — `magpie`, the corvid that gathers everything into one nest, a bird as crow and finch are. The position column is `_pos`, a name no table of a program is likely to use; a frame that holds one is refused. A value looked up is written as text so that one function serves every column kind, compared with `str` of the column on both sides and read by the kernel as the column's kind for its filter.

**Design Note: a manifest, and keys declared once.** Considered: the directory as the catalog, as the first architecture had — every read listed the log and read every file's head to decide what to open (rejected 2026-10-26: the listing was the index, a merge's switch was two steps a crash could split, and nothing said which files were live); keys given at every call — `batch[d, f, by = …]`, `merge[d, by = …]`, `latest[d, by]` (rejected: a log sorted by one key at write and merged by another is a mess nobody wants, and `latest` by a column that is no key is a group over `scan`, in Crow); a second declared sort order, so a reverse-edges log for a graph would be the merge's work (rejected for now: a second order is a second log the program writes, two `batch` calls, and a package over Magpie does that; a declared order would double every merge for every log). Decided: `dir/manifest`, a Magpie file of one group naming the live segments (each its level, position range, rows, bytes and key ranges) with the log's keys in its key list and its declarations — the time column — in its notes, written beside and renamed over the old one; the batches stay the tail the directory lists. The first batch declares the keys; `merge`, `latest` and `commit` read them from the manifest and take no `by`; a batch naming other keys is refused naming both. What the manifest does not name is a leftover the next merge removes.

**Design Note: the executor as operators.** Considered: a query engine linked, as DataFusion (rejected 2026-10-26, Vijay's rule: nothing third-party in Magpie); a planner and a vectorised executor of our own, with a query vocabulary in Crow to drive it (rejected as a phase: a multi-year engine, and the boundary stated under what Magpie does not do). Decided: one kernel for the shape most analytics takes — filter, group, aggregate, sort — as separate operators over row groups (scan pruned by statistics, filter by predicates over column vectors, group by the keys' bytes, reduce into partials, combine), so a verb is a fixed composition and a later door a translator; predicates as three lists (`on`, `ops`, `equal`) because a mask is an expression no row can take and values written as text are what `lookup` already takes; the population variance, as the frame module's `group` answers it; `first` and `last` by position, since the groups run on every core at once. The as-of join beside it, over each key's run, for the point-in-time join a feature store is built on. Not here: joins of two large logs in one plan, subqueries, window functions — loops over windows in Crow.

**Design Note: search's long tail, in our own code.** Considered: Lucene's engine linked, as tantivy (rejected 2026-10-26, Vijay's rule: nothing third-party in Magpie). Decided: the pieces Lucene's long tail is made of, each written here and held to the scan — postings with positions per text column per row group, built by the merge beside the token filter (the filter stays: it answers whether a word can be in a group in microseconds, where a dictionary is parsed per group); a sorted dictionary, so a prefix is a run of it and a fuzzy word a walk of it with the edit distance cut at two; a block bound (the block's largest count and shortest document) so a top-k over a common word skips the blocks that cannot beat the k-th, at the granularity of a block of 128 postings and of a group; the Porter stemmer, declared per log so the index and the query agree; a snippet around the first hit; facets a `group` over the answer, in Crow. Not here: analysers beyond letters and digits lowercased, stemmers beyond English, Lucene's query DSL. The forms' syntax is Lucene's own inside the words (`kit*`, `kitchn~`, a space for a phrase), since a word is a text the program hands over and no syntax of the language's is touched.

**Design Note: the sequencer.** Considered: every write a file of its own, as the first architecture had — a row per request a file per request, thousands a second without a flush and hundreds with (rejected 2026-10-26: Redis takes single-key writes at memory speed, and Postgres groups its commits); a server process of the log's own, as Redis and Postgres are, every write a request to it (rejected for now: a log is a directory a program opens, and a served app is that process; the doors of phase 9 make it reachable from outside). Decided: one structure per log in the process — the memtable and its write-ahead log, which every durable database has — holding the rows written since the last flush with the positions they were given as they arrived, each key's last position, and the image of the newest row per key; every write of the process goes through it under its lock, a thread flushes what is pending as one batch file every ten milliseconds and fsyncs it (a hundred a second is nothing), and the readers of the process see the pending rows at once because they are served as a file named `<dir>/.pending@first-last`, a Magpie file in memory the readers open as any other — one reader for the files and the memtable, as design rule 1 asks. The name carries the positions the listing saw, so a reader that opens it after the thread flushed those rows is handed the file they went to, and a listing reads the pending rows before it lists the files, leaving them out where a file covers them: a flush between the two steps hides nothing and doubles nothing (the first version listed the files first, and a `head` asked within ten milliseconds of a `put` had answered -1). Positions a put assigns are provisional until flushed where another process writes the same log; one writer process is the design, and the kernel's claim of a batch number is the safety net it always was.

**Design Note: reads bounded by what a frame holds.** Considered: a read that answers a stream, so a billion rows could be walked by one call (rejected 2026-10-26: the language has one shape for rows, a frame, and a stream of frames is the loop the program writes). Decided: every read is bounded — `since` and `scan` by a position window, `latest` by a range of the log's first key, `lookup` and `search` by their keys and `k` — and a read over the whole log is a loop over windows in Crow, each window reading its segments and its columns and nothing else; an aggregate over the whole log stays such a loop until the executor of phase 8 pushes the common ones below the reader.

**Design Note: indexes built by the merge, never by the producer.** Considered: the producer naming the columns to index (`texts` on `batch`, as the first architecture had; rejected 2026-10-26, Vijay's question: an ingestion job should not know what will be asked of its rows, and a column it did not name was unsearchable until the log was rewritten); every batch indexing every text column (rejected: the price on the write path for columns never searched, and the decision still at ingestion). Decided: the merge indexes every text column of every segment it writes, per row group, giving a column up where its distinct tokens exceed half its documents (an identifier column: a filter of every value prunes nothing); a search reads an indexed group through its filter and any other group whole, and scores both the same, so a row is searchable the moment it lands, cheap once merged, and no producer decides either. A batch's own words are not indexed: the tail is small because the merge runs.

**Design Note: the streaming merge and its levels.** Considered: every merge folding every file into one segment, as the first architecture had (rejected 2026-10-26: the merge stacked every live file into one frame, sorted it and wrote the segment into one buffer — it ended at RAM — and every merge rewrote the whole log); segments in position order with blooms alone for the keys (rejected: it gives up the one-group lookup by the keys a segment is sorted by, the thing the measure showed); key-ordered levels with disjoint ranges, as LevelDB keeps them (rejected: a log compacts by time, and disjoint key ranges make `since` read every segment). Decided: a k-way merge over inputs that are already sorted by the keys then position, one row group per input and one for the output in memory, the newest version of a key the last of its run; segments of at most a gigabyte, named by a counter since a merge that splits by size makes two over one position range; levels with a fan-out of eight, the tail folding into level 1 and a level's oldest eight into the next, so a merge touches a slice and a billion rows are a few dozen segments; across segments the newest position wins at read, which `lookup` and `latest` already do.

**Design Note: Magpie's own file format.** Considered: Arrow IPC for a batch and Parquet for a segment, as the first architecture had, the statistics as one JSON text in the file's head (rejected 2026-10-26: no third-party code in Magpie — Vijay's rule; and three costs of their own: the head was parsed whole by every query of any column, tens of megabytes at a thousand columns; Parquet keeps a footer entry per column per row group, so a billion rows in groups of 8192 was the known wide-table pathology; every write converted the frame to Arrow and every read converted it back). Decided: one format for a batch, a segment and the manifest, designed around the frame's columns — a chunk is a column's cells over a row group as the frame holds them, encoded by its kind; the index is per column, found through a two-level footer, so a reader reads the one column's one group; the codec is our own, applied where it pays.
