# Crow UI Framework

> **Status note:** this is the UI framework's design/vision document,
> written before `view` blocks, named-argument attributes, and the chart
> and style modules shipped. The shipped surface is specified in
> `language-spec.md` (Built-in Module: web → View Blocks, Charts, Styling)
> and taught in the book (chapters 11–12). Code sketches below may use
> pre-current syntax (`page[path, render, handle]`,
> `chart.live[...]`), and the phase sections describe features that may
> not exist yet.

## Overview

Crow's UI framework enables full-stack web applications written entirely in Crow. No JavaScript, no HTML, no CSS by hand. The developer writes functions per route using element functions, reactive data loading, and two-way binding. The framework handles rendering, diffing, and real-time updates over WebSocket.

Built on top of Crow's `web` module using `page` routes. Inspired by Phoenix LiveView. Adapted to Crow's "pseudocode that runs" philosophy (Principle #5).

## Design Principles

1. **One language.** Frontend and backend are both Crow. No React, no npm, no node_modules.
2. **One server.** UI is a `page` route on the same `web` app as API routes. No separate server, no port conflicts.
3. **Reactive assignments.** `data = fetch[url]` and `data = poll[url, 5]` are reactive — they update the variable and trigger re-renders automatically. No callbacks, no `useEffect`, no `setInterval`.
4. **Two-way binding.** `field['Label', var]` and `select[options, var]` read from and write to the variable directly. No `onChange` callbacks, no setter functions.
5. **Frames for data.** `Value::Frame` (columnar data) is the primary data structure. `table[frame]` auto-renders headers and rows. Masks (`f[mask]`), `group`, `sort` operate on whole columns. No per-row iteration.
6. **Server-side rendering.** The render function runs on the server (Crow transpiles to Rust, not JS). A tiny JS runtime (~30 lines) forwards DOM events over WebSocket and patches the DOM with diffs.
7. **Charts from scratch.** No external JS chart libraries. Static charts are SVG generated by pure Crow functions. Interactive charts use a custom Crow-built canvas engine.
8. **Hooks for client-side interactivity.** Some interactions (zoom, pan, crosshair at 60fps) cannot round-trip to the server. A `hook` mechanism bridges server-managed data to client-side JS widgets for visual-only interactions.

## The Reactive Pattern

### How It Works

A `page` route uses a render function. After `use ui`, all element functions are available directly — no `ui.` prefix needed (except `ui.input`, which conflicts with the built-in `input`). Top-level variables are reactive state. Named functions are event handlers — pass them directly to event attributes. After each event, the runtime re-renders and sends the diff to the browser.

```
use web, ui

count = 0

fn inc[]
    count = count + 1

fn dec[]
    count = count - 1

view render[]
    return div[
        h1['Count: `count`'],
        button['+', click = inc],
        button['-', click = dec]
    ]

serve[3000]
page['/', render]
```

No `state.get`. No `state.set`. No `handle` function with string dispatch. No init function. No update function. No model struct with all fields copied on every change. Variables declared at the top level are automatically persisted across renders. The transpiler handles the plumbing.

### Reactive Data Loading

`fetch` and `poll` return reactive handles. The runtime updates the variable and triggers a re-render when data arrives. No callbacks, no lambdas.

```
use web, ui, frame

playbooks = fetch['/api/playbooks']
positions = poll['/api/positions', 5]
trades = poll['/api/trades', 5]
```

- `fetch[url]` — one-time HTTP GET. Returns data (as frame if JSON array, map otherwise). Updates the variable when the response arrives.
- `poll[url, seconds]` — repeating HTTP GET every N seconds. Updates the variable on each tick.

No `setInterval`. No `useEffect`. No `async/await`. One line per data source.

### Two-Way Binding

`field` and `select` read from and write to a reactive variable directly. No `onChange` callback.

```
min_vol = 100000
min_price = 2.0
filter_pb = 'all'

view render[]
    return div[
        field['Min Vol', min_vol],
        field['Min $', min_price],
        select[unique[data.playbook_code], filter_pb]
    ]
```

- `field[label, var]` — renders a labeled input. Reads the current value of `var`, writes user input back to `var`.
- `select[options, var]` — renders a dropdown. Options is an array of strings. Reads `var` for the selected value, writes user selection back to `var`.

No callbacks. The binding is implicit. The variable is reactive — changes trigger re-render.

### Events

For interactions, pass a function reference directly to an event attribute:

```
fn inc[]
    count = count + 1

fn dec[]
    count = count - 1

button['+', click = inc]
button['-', click = dec]
```

No string event names. No central `handle` function with `if event eq ...` dispatch. Each event handler is a named function. The transpiler generates the dispatch automatically.

Event attributes: `click`, `input`, `change`, `submit`, `focus`, `blur`.

### Real-time — poll

For periodic updates, use `poll` — the runtime manages the timer:

```
positions = poll['/api/positions', 5]
```

The variable updates every 5 seconds. Each update triggers a re-render. The developer never touches threads, channels, or async.

### Side Effects

Side effects happen directly in event handlers. Crow runs on the server — blocking is fine.

```
data = frame[]

fn refresh[]
    data = query[db, 'SELECT * FROM prices']
```

No `Cmd` type. No async. The server just does the work and assigns to reactive variables.

## How It Works (Runtime)

```
Browser                          Server (Crow/Rust)
  |                                  |
  |  ← initial HTML (full page)  ←  | render[] produces VNode tree
  |                                  |
  |  click "+" button                |
  |  → WebSocket: "inc"          →  |
  |                                  | inc[] runs, mutates reactive vars
  |                                  | re-render → VNode diff
  |  ← VNode patch (JSON)         ←  | send only changed nodes
  |                                  |
  |  type in field/select            |
  |  → WS: {field, value}         →  |
  |                                  | two-way binding → reactive var updated
  |  ← VNode patch              ←  | re-render + diff
  |                                  |
  |  (every N seconds from poll)     |
  |                                  | fetch new data → reactive var updated
  |  ← VNode patch              ←  | re-render + diff
```

The JS runtime is ~30 lines:
1. Open WebSocket to server
2. Listen for `click`, `input`, `change`, `submit` events on elements with `data-event` / `data-crow-*` attributes
3. Send the event ID (and value for inputs) over WebSocket
4. Receive VNode patch from server, apply DOM updates

The server holds state in memory per connection. Each WebSocket connection = one user session = one state instance.

## Frame Integration

### table[frame]

When `table` receives a `Value::Frame`, it auto-renders headers and rows from the frame schema. No manual `for` loop, no `tr`/`td` markup.

```
use web, ui, frame

data = poll['/api/positions', 5]
table[data]
```

This renders a full HTML table with column headers from frame column names, and one row per frame row. For filtered/sorted data:

```
filtered = data[data.price >= 10]
sorted = sort[filtered, pnl, desc]
table[sorted]
```

### Frame operations in UI

All frame builtins work in render functions:

```
fn performance[trades]
    today_trades = trades[trades.date eq fmt[now[], style = 'date']]
    summary = group[today_trades, playbook_code, [pnl, sum], [pnl, count], [pnl, mean]]
    summary = sort[summary, pnl_sum, desc]
    table[summary]
```

- `frame[mask]` — vectorized filter on columns
- `group[frame, key, [col, agg], ...]` — group + aggregate in one scan
- `sort[frame, col, dir]` — sort by column
- `head[frame, n]` — first N rows
- `unique[frame.col]` — unique values in a column

## View Functions

### DOM Elements

Element functions produce VNode trees. No closing tags, no JSX.

```
fn my_page[]
    div[
        header[
            h1['My App'],
            nav[
                a['Home', href = '/'],
                a['About', href = '/about']
            ]
        ],
        main[
            p['Hello world']
        ],
        footer[
            p['Built with Crow']
        ],
        class = 'app'
    ]
```

Available elements:
- **Layout:** `div`, `span`, `main`, `header`, `footer`, `section`, `nav`, `aside`
- **Text:** `h1` ... `h6`, `p`, `pre`, `code`
- **Interactive:** `button`, `ui.input`, `select`, `form`, `textarea`
- **Data:** `table`, `ul`, `ol`, `li`
- **Media:** `img`, `a`
- **Grouping:** `fragment` (no wrapper element)

> **Note:** `ui.input` keeps the `ui.` prefix because `input` is a built-in function (CLI input reading). All other element names have no conflicts.

### Attributes

Attributes are named arguments. Event handlers use function references.

```
--- static attributes
div[id = 'main', class = 'card']
img[src = '/logo.png', alt = 'Logo']

--- event attributes (function references)
button['Save', click = save]
button['Delete', click = delete_item]

--- two-way binding (no event handler needed)
query = ''
symbol = 'AAPL'
field['Search', query]
select[symbols, symbol]
```

Event attributes: `click`, `input`, `change`, `submit`, `focus`, `blur`.

### Conditional Rendering

Use `if` — it's just Crow.

```
loading = false
data = frame[]
error = ''

view render[]
    div[
        if loading
            p['Loading...']
        else
            table[data],
        if len[error] gt 0
            p[error, class = 'error']
    ]
```

### Lists

Use `for` — it's just Crow.

```
items = []

view render[]
    ul[
        for item in items
            li['`item.name`: `item.price`']
    ]
```

### Reusable Views

"Components" are just functions. No component system needed.

```
fn card[title, value]
    div[
        h3[title],
        p[class = 'value', str[value]],
        class = 'card'
    ]

fn stat_row[positions, total_pnl, win_rate]
    div[
        card['Total P&L', total_pnl],
        card['Open Positions', len[positions]],
        card['Win Rate', '`win_rate`%'],
        class = 'stats'
    ]

positions = poll['/api/positions', 5]

view render[]
    div[
        stat_row[positions, sum[positions.pnl], 65],
        table[positions]
    ]
```

## Design Decisions

### 1. State — reactive variables

All state lives on the server as reactive variables. Top-level assignments (e.g., `count = 0`) are automatically persisted in `CrowLiveState` across renders. No client-side state, no cookies, no localStorage. Each WebSocket connection has its own state instance. If the connection drops, state is gone — reconnect creates a fresh state.

For persistence across reconnects, store state in the database:

```
fn save[]
    exec[db, 'INSERT INTO saved_state ...']
    saved = true
```

### 2. Real-time — poll

No polling loops. Use `poll[url, seconds]` for periodic data. The runtime manages the timer. The developer never touches threads, channels, or async.

### 3. CSS — external file or inline

Crow does not generate CSS. Use a static CSS file served via `static_dir`:

```
use web

static_dir['/css', 'static/css']
```

Or use inline styles via the `style` attribute:

```
div[style = 'padding: 16px; border: 1px solid #ddd']
```

Use any CSS framework (Tailwind, Pico, etc.) via a static file.

### 4. Routing — page routes

Each page is a separate `page` route. No client-side router.

```
use web, ui

view home_render[]
    div[
        nav[a['Home', href = '/'], a['About', href = '/about']],
        h1['Welcome']
    ]

view about_render[]
    div[
        nav[a['Home', href = '/'], a['About', href = '/about']],
        h1['About']
    ]

serve[3000]
page['/', home_render]
page['/about', about_render]
```

Each route has its own state. Navigation is standard links. For shared layouts, extract a layout function.

### 5. Forms — two-way binding + event handlers

Form inputs use two-way binding via `field`. Submit triggers validation in a named handler.

```
email = ''
password = ''
error = ''

fn login[]
    if len[email] eq 0
        error = 'Email required'
    else
        error = ''

view render[]
    form[
        field['Email', email],
        field['Password', password],
        if len[error] gt 0
            p[error, class = 'error'],
        button['Log in', click = login]
    ]

serve[3000]
page['/login', render]
```

### 6. Error handling — reactive variables

Errors are just variables. If an HTTP request fails, assign the error. The view renders it.

```
error = ''
data = frame[]

fn do_fetch[]
    result = get['https://api.example.com/data']
    if result.ok
        data = result
        error = ''
    else
        error = result.reason

view render[]
    return div[
        button['Fetch', click = do_fetch],
        if len[error] gt 0
            p[error, class = 'error'],
        if len[data] gt 0
            table[data]
    ]

page['/errors', render]
```

### 7. Performance

The server re-renders the full handler on every event. For simple apps this is fast (sub-millisecond in Rust). For large DOMs, the `morphdom` JS library diffs and patches only changed elements.

For high-frequency interactions (drag, scroll, resize), these stay client-side in the JS runtime — no server round-trip. The JS runtime handles `mousemove` locally and only sends a final event to the server.

### 8. Authentication and Sessions

*Superseded (2026-09-29): the session layer's `reader`, `sign_in` and `sign_out` shipped instead of `session.get/set`, and a page for signed-in readers checks `reader` in its view; `auth = true` on a page was rejected (spec, Who the reader is, and the Design Note "no `auth` on a page").*

Each WebSocket connection has its own `state`. Authentication adds a `session` that persists across page navigations within the same browser. The `session` is a signed cookie — the server validates it on each WebSocket connect.

```
use web, ui

--- login page (no auth required)
email = ''
password = ''
error = ''

fn do_login[]
    user = query[db, 'SELECT * FROM users WHERE email = \'`email`\'']
    if user and verify[user.password_hash, password]
        session.set['user_id', user.id]
        session.set['user_name', user.name]
        redirect['/']
    else
        error = 'Invalid credentials'

view login_render[]
    return form[
        field['Email', email],
        field['Password', password],
        if len[error] gt 0
            p[error, class = 'error'],
        button['Log in', click = do_login]
    ]

--- protected page
fn do_logout[]
    session.clear[]
    redirect['/login']

view home_render[]
    user = session.get['user_name']
    return div[
        h1['Welcome, `user`'],
        button['Log out', click = do_logout]
    ]

secret[env['SECRET_KEY']]
serve[3000]
page['/login', login_render]
page['/', home_render]
```

Key API:
- `secret[key]` — enables signed session cookies (called before `serve[]`)
- `session.set[key, value]` — store a value in the session
- `session.get[key]` — retrieve a value from the session
- `session.clear[]` — destroy the session (logout)
- `redirect[path]` — navigate to another route

### 9. URL Parameters

> **Shipped (September 2026), differently:** a path's `:name` segment is a
> fact in the page's address — `page['/trade/:trade', trade_render]` opens a
> session with the fact `trade` read from the path, and the address follows
> the fact — as `url = […]` puts facts in the query string. There is no
> `init` function or `params` record: the page's state is its facts. See
> the spec, Core (Server), and its Design Note *a page's address and its
> head*.

Dynamic route segments and query parameters. Route params use `:name` syntax.

```
--- route parameters
trade = nil
trade_id = ''

fn trade_init[params]
    trade_id = params.id
    trade = query[db, 'SELECT * FROM trades WHERE id = `params.id`']

view trade_render[]
    return div[
        h1['Trade `trade_id`'],
        p['Symbol: `trade.symbol`'],
        p['P&L: `trade.pnl`']
    ]

page['/trade/:id', trade_render, init = trade_init]

--- query parameters
q = ''
results = frame[]

fn search_init[params]
    q = params.q or ''
    results = query[db, 'SELECT * FROM items WHERE name LIKE \'%`q`%\'']

view search_render[]
    return div[
        field['Search', q],
        table[results]
    ]

page['/search', search_render, init = search_init]
--- accessed via /search?q=hello

--- multiple route params
user = nil
trade = nil
trade_id = ''

fn user_trade_init[params]
    trade_id = params.trade_id
    user = query[db, 'SELECT * FROM users WHERE id = `params.user_id`']
    trade = query[db, 'SELECT * FROM trades WHERE id = `params.trade_id`']

view user_trade_render[]
    return div[
        h1['`user.name` — Trade `trade_id`']
    ]

page['/user/:user_id/trade/:trade_id', user_trade_render, init = user_trade_init]
```

The `init` function receives `params`. Route segments (`:id`) and query string (`?q=hello`) are both available on `params`. Init functions assign to reactive variables, which are then available in render functions.

### 10. Shared Layout

Wrap multiple routes in a shared layout. Extract a layout function and call it from each render function.

```
use web, ui

fn app_layout[user, content]
    return div[
        header[
            div['Trading App', class = 'logo-text'],
            nav[
                a['Dashboard', href = '/'],
                a['Positions', href = '/positions'],
                a['Settings', href = '/settings']
            ],
            if len[user] gt 0
                span[user, class = 'user'],
            class = 'main-header'
        ],
        main[content],
        footer[p['Built with Crow']],
        class = 'app'
    ]

--- each route uses the layout
user = session.get['user_name']
ohlcv = poll['/api/ohlcv', 5]

view dash_render[]
    return app_layout[user, div[
        h1['Dashboard'],
        table[ohlcv]
    ]]

positions = poll['/api/positions', 5]

view pos_render[]
    return app_layout[user, div[
        h1['Positions'],
        table[positions]
    ]]

serve[3000]
page['/', dash_render]
page['/positions', pos_render]
```

The layout is a function that takes data and a content VNode. No special component system — just functions calling functions.

### 11. Debounce

*Rejected (2026-09-29): a derivation has one recompute in flight, the latest input winning, and a second click on a running handler is dropped (spec, Design Note "no debounce").*

Typing in a search input fires `input` on every keystroke. Debounce delays the server call until the user stops typing.

```
--- without debounce: field fires on every keystroke
field['Search', query]

--- with debounce: fires 300ms after last keystroke
field['Search', query, debounce = 300]
```

`debounce = ms` is handled by the client-side JS runtime. It delays sending the WebSocket event until `ms` milliseconds have passed with no new input. The server never knows about intermediate keystrokes.

Also available on other events:
```
--- debounce a button click (prevent double-click)
button['Save', click = save, debounce = 500]
```

### 12. File Upload

File uploads use `ui.input[type = 'file']`. The file is sent to the server via WebSocket as binary data. The handler receives file metadata.

```
file = nil
error = ''
uploaded = false

fn file_selected[value]
    file = value

fn upload[]
    if file
        write['/uploads/`file.name`', file.data]
        uploaded = true
    else
        error = 'No file selected'

view render[]
    return form[
        ui.input[type = 'file', change = file_selected, accept = '.csv,.xlsx'],
        if len[error] gt 0
            p[error, class = 'error'],
        if uploaded
            p['Uploaded `file.name`', class = 'success'],
        button['Upload', click = upload]
    ]

page['/upload', render]
```

File object properties:
- `file.name` — original filename
- `file.size` — size in bytes
- `file.type` — MIME type
- `file.data` — binary content

For large files, the runtime streams chunks over WebSocket. A `max_size` option limits upload size:
```
ui.input[type = 'file', change = file_selected, max_size = 10_000_000]
```

### 13. Keyboard Events

*Superseded (2026-09-29): a key presses a drawn element, `button['Save', click = save, shortcut = 'ctrl+s']`, instead of `keydown` handlers (spec, Design Note "keys press elements").*

`keydown` and `keyup` events on any element. Keyboard shortcuts on the document level.

```
q = ''
results = frame[]

fn search_key[value]
    if value eq 'Enter'
        results = query[db, 'SELECT * FROM items WHERE name = \'`q`\'']

--- keydown on a specific element
ui.input[type = 'text', keydown = search_key]

--- global keyboard shortcuts
modal = nil

fn on_keydown[value]
    if value eq 'ctrl+s'
        do_save[]
    else if value eq 'Escape'
        modal = nil

view render[]
    return div[
        h1['Press Ctrl+S to save']
    ]

page['/', render]
```

Key handler receives:
- `value` — key name (`'Enter'`, `'Escape'`, `'a'`, `'ArrowUp'`, `'ctrl+s'`, etc.)

Global `keydown`/`keyup` events are sent to the handle function. On a specific element, they fire only when that element has focus.

### 14. Loading States

Slow operations (DB queries, API calls) need visual feedback. Set a loading flag in state before and after the slow operation.

```
loading = false
data = frame[]

fn load[]
    loading = true
    data = query[db, 'SELECT * FROM big_table']
    loading = false

view render[]
    return div[
        button['Load Data', click = load],
        if loading
            p['Loading...', class = 'spinner']
        else if len[data] gt 0
            table[data]
    ]

page['/', render]
```

Since Crow is server-side and synchronous, the runtime sends an intermediate render before the slow operation starts (showing the loading state), then sends the final render when the operation completes.

### 15. Page Title and Head

> **Shipped (September 2026):** `title[text]` and `meta[name = …, content =
> …]` are elements a view places anywhere in its tree (not statements before
> its `return`); a served page carries them in its head, and a render that
> changes them changes the tab. `meta` takes attributes, which pass through
> as HTML. `link[…]` was not built: a stylesheet is `css/app.css`, and files
> are `static_dir`. See the spec, LiveView / Pages.

Set the page title, favicon, and meta tags per route.

```
view dash_render[]
    title['Dashboard — Trading App']
    meta[name = 'description', content = 'Real-time trading dashboard']
    return div[h1['Dashboard']]

view pos_render[]
    title['Positions — Trading App']
    return div[h1['Positions']]

serve[3000]
page['/', dash_render]
page['/positions', pos_render]
```

- `title[text]` — sets the page `<title>` tag
- `meta[name, content]` — sets a `<meta>` tag
- `link[rel, href]` — adds a `<link>` tag (for favicon, stylesheets)

These are rendered into the `<head>` of the initial HTML page. On navigation between `page` routes, the title is updated dynamically.

### 16. Security

The framework automatically handles common web security concerns.

**HTML escaping (XSS prevention):**

All string values rendered into HTML are automatically escaped. No raw HTML injection.

```
--- safe: angle brackets are escaped
name = '<script>alert("xss")</script>'
p[name]
--- renders: <p>&lt;script&gt;alert("xss")&lt;/script&gt;</p>
```

For intentional raw HTML (rare), use `raw`:
```
raw['<svg>...</svg>']
```

**CSRF protection:**

Forms submitted over WebSocket are already protected — the WebSocket connection is authenticated by the session cookie. No CSRF tokens needed for `live` routes.

For standard `route` endpoints (non-WebSocket), CSRF tokens are generated automatically:
```
fn action_handler[req]
    --- process the action
    return json[map[ok = true]]

route['/api/action', 'POST', action_handler]
--- CSRF token validated automatically for POST/PUT/DELETE
```

**Session security:**
- Session cookies are signed with `secret[key]` (called before `serve[]`)
- `httponly`, `secure`, `samesite = 'strict'` flags set by default
- Session expiry: `secret[key, session_max_age = 86400]` (seconds)

**Content Security Policy:**

Set CSP headers to restrict what the browser can load:
```
csp['default-src \'self\'']
```

## Packages

### `ui` — core package

Provides: `page[path, render]`, `div`, `button`, `field`, `select`, `table`, `ui.input`, etc.

Also provides the JS runtime that gets embedded in the initial HTML page.

```
--- page[path, render]
--- mounts a page route (implicit app)
--- manages WebSocket connections per session

use web, ui

view render[]
    h1['Hello']

serve[3000]
page['/', render]
```

### `chart` — two-tier chart system

#### Tier 1: `chart.candle`, `chart.line`, etc. — server-rendered SVG

Pure functions that take data, return SVG strings. No JavaScript. Used for static views, thumbnails, reports, monitoring dashboards that auto-refresh.

```
ohlcv = poll['/api/ohlcv', 5]

view chart_render[]
    return div[
        chart.candle[ohlcv, width = 800, height = 400],
        chart.volume[ohlcv, width = 800, height = 100],
        chart.line[ohlcv.close, color = '#2196f3']
    ]

page['/dashboard', chart_render]
```

Chart types:
- `chart.candle[data]` — candlestick (OHLCV)
- `chart.line[data]` — line chart
- `chart.bar[data]` — bar chart
- `chart.volume[data]` — volume bars
- `chart.scatter[x, y]` — scatter plot
- `chart.heatmap[matrix]` — heatmap
- `chart.pie[data]` — pie chart

SVG primitives (used internally, also available):
- `chart.svg[w, h, content]` — SVG wrapper
- `chart.rect[x, y, w, h, fill]` — rectangle
- `chart.circle[cx, cy, r, fill]` — circle
- `chart.text[x, y, content]` — text label
- `chart.path[d]` — arbitrary SVG path

#### Tier 2: `chart.live` — interactive canvas chart (hook)

For trading dashboards and interactive analysis. Full client-side interactivity: zoom, pan, crosshair, tooltips at 60fps. The chart engine runs on the client (Canvas/JS). Data comes from the server.

`chart.live` is a **hook** — it bridges server-managed data to a client-side interactive widget. The server owns the data; the client owns the rendering and visual interactions.

```
symbol = 'AAPL'
tf = '1m'
ohlcv = poll['/api/ohlcv?symbol=`symbol`&tf=`tf`', 1]
trades = poll['/api/trades?symbol=`symbol`', 5]
support = fetch['/api/levels?symbol=`symbol`&type=support']

view render[]
    return div[
        chart.live[ohlcv, height = 400, timeframe = tf,
            chart.indicator['volume'],
            chart.indicator['macd_band'],
            chart.overlay['line', price = support, color = '#16a34a', label = 'Support'],
            for t in trades
                chart.marker[t.timestamp, t.price, type = t.side]
        ],
        class = 'chart-container'
    ]

page['/trading', render]
```

**How `chart.live` works:**

```
Browser                                Server (Crow/Rust)
  |                                        |
  |  ← initial HTML + chart data (JSON) ←  | handler renders, chart.live serializes OHLCV
  |                                        |
  |  JS runtime detects data-chart div     |
  |  → initializes canvas chart engine     |
  |  → renders candles, indicators         |
  |                                        |
  |  user zooms/pans/crosshair             |  (no server round-trip)
  |  → handled entirely client-side        |
  |                                        |
  |  (interval fires every 1000ms)         |
  |                                        | re-query DB, re-render handler
  |  ← new OHLCV data (JSON diff)      ←  | chart.live detects data changed
  |                                        |
  |  JS runtime appends new bars           |
  |  → chart updates without re-creating   |
  |                                        |
  |  user clicks a candle bar              |
  |  → WS: {event_id, bar_data}        →  | click handler in Crow runs
  |                                        | selected_bar = bar_data
  |  ← HTML diff (detail panel updated) ←  | re-render, only detail panel changed
```

**What stays client-side** (inside the chart engine, no server round-trip):
- Canvas rendering of candles, lines, bars
- Crosshair following mouse position
- Zoom (scroll wheel, pinch)
- Pan (click-drag)
- Tooltip display on hover
- Indicator pane layout and resize

**What flows server → client** (data updates):
- OHLCV data (initial load + incremental updates)
- Indicator values (MACD colors, moving averages)
- Overlay positions (support/resistance levels)
- Trade markers (entry/exit points)

**What flows client → server** (user actions that need server state):
- Bar click (to show trade details)
- Range selection (to analyze a time window)
- Timeframe change (to re-query data)

`chart.live` sub-elements:
- `chart.indicator[name]` — add an indicator pane (volume, macd_band, rsi, etc.)
- `chart.overlay[type, ...]` — add an overlay on the price pane (line, band, channel)
- `chart.marker[timestamp, price, ...]` — add a point marker (trade entry/exit, signal)
- `chart.sync[group = name]` — sync zoom/scroll with other `chart.live` instances in the same group

#### Custom chart engine (design decision)

Crow builds its own interactive chart engine from scratch. No klinecharts, no lightweight-charts, no third-party JS charting library. The engine is a Canvas/JS module bundled with the `chart` package.

**Why build from scratch:**
- Full control over rendering, interactions, and data format
- No external JS dependencies — consistent with Crow's "one language" principle
- Optimized for Crow's data flow (server-managed data, JSON diffs)
- Can evolve with Crow's needs without upstream library constraints

**Engine requirements:**
- Canvas-based rendering (not SVG — performance for thousands of candles)
- OHLCV candlestick rendering with configurable colors
- Volume pane with separate y-axis
- Custom indicator panes (MACD band, RSI, moving averages)
- Crosshair with price/time labels
- Zoom (scroll wheel, pinch-to-zoom) with smooth animation
- Pan (click-drag horizontal scrolling)
- Tooltip on hover showing OHLC values
- Overlay support (horizontal lines, bands, markers)
- Trade markers (entry/exit arrows with connecting lines)
- Chart sync (multiple charts scroll/zoom together)
- Resize handling (responsive to container size changes)
- Incremental data updates (append new bars without re-creating chart)
- Dark theme by default (matching typical trading UI aesthetics)

### Modals and Dialogs

Modals are variable-driven. Show/hide is controlled by a reactive variable. No special component needed.

```
modal = ''
items = fetch['/api/items']
selected_id = 0

fn show_confirm[]
    modal = 'confirm'

fn confirm_delete[]
    exec[db, 'DELETE FROM items WHERE id = `selected_id`']
    modal = ''

fn cancel[]
    modal = ''

view render[]
    return div[
        button['Delete', click = show_confirm],
        table[items],
        if modal eq 'confirm'
            div[
                div[
                    h3['Are you sure?'],
                    p['This action cannot be undone.'],
                    div[
                        button['Delete', click = confirm_delete],
                        button['Cancel', click = cancel],
                        class = 'modal-actions'
                    ],
                    class = 'modal'
                ],
                class = 'modal-overlay'
            ]
    ]

page['/', render]
```

For reusability, extract a modal view function:

```
fn confirm_modal[modal, title, message, on_confirm, on_cancel]
    if modal eq 'confirm'
        return div[
            div[
                h3[title],
                p[message],
                div[
                    button['Confirm', click = on_confirm],

                ],
                class = 'modal'
```

### Flash Messages

Temporary messages that auto-dismiss. The server sets the message; the client-side runtime removes it after a timeout.

```
flash_msg = ''
flash_type = 'success'

fn save[]
    exec[db, 'INSERT INTO items ...']
    flash['Item saved successfully', 3000]

view render[]
    return div[
        button['Save', click = save],
        if len[flash_msg] gt 0
            div[flash_msg, class = 'flash `flash_type`']
    ]

page['/', render]
```

- `flash[message, timeout]` — sets flash message and schedules auto-clear after `timeout` ms
- `flash[message, timeout, type = 'error']` — with type (`'success'`, `'error'`, `'warning'`, `'info'`)

The runtime sends a timed re-render to clear the flash. The developer doesn't manage timers.

### Pagination

Server-side pagination for large datasets. The developer controls page size and current page in state.

```
pg = 1
per_page = 20
total = 0
items = frame[]

fn load_page[]
    total = query[db, 'SELECT count[] FROM items'].0.count
    items = query[db, 'SELECT * FROM items ORDER BY id LIMIT `per_page` OFFSET `[pg - 1] * per_page`']

view render[]
    return div[
        table[items, cols = ['id', 'name', 'price']],
        paginate[total, per_page]
    ]

page['/items', render]
```

`paginate[total, per_page]` renders page navigation buttons and updates the current page on click:

```
--- renders: « ‹ 1 2 3 4 5 › »
--- clicking a page number updates the page and re-renders
```

For custom pagination UI, use reactive variables and named handlers:

```
fn prev_page[]
    pg = max[1, pg - 1]

fn next_page[]
    pg = min[ceil[total / per_page], pg + 1]

fn pagination_bar[pg, total, per_page]
    pages = ceil[total / per_page]
    return div[
        button['‹', click = prev_page],
        span['Page `pg` of `pages`'],
        button['›', click = next_page],
        class = 'pagination'
    ]
```

### Table Features

*Superseded (2026-09-29): `table[frame, sort = true]` shipped, the session keeping each table's order; click, key, actions and hide are the table's other named arguments, and filtering stays the program's (spec, Tables over frames, and the Design Note "no filter on a table").*

The `table` element supports sorting, filtering, and column configuration.

```
--- basic table
table[items]

--- with column selection
table[items, cols = ['symbol', 'qty', 'entry', 'pnl']]

--- with column headers
table[items, cols = [
    [key = 'symbol', label = 'Symbol'],
    [key = 'qty', label = 'Quantity'],
    [key = 'pnl', label = 'P&L']
]]

--- with sorting (calls handler with column name)
table[items, cols = ['symbol', 'qty', 'pnl'], [sort = sort_col]]

--- with row click (calls handler with row data)
table[items, cols = ['symbol', 'pnl'], [row_click = select_row]]
```

Sorting and row click are handled by named functions:

```
fn sort_col[value]
    items = query[db, 'SELECT * FROM items ORDER BY `value`']

fn select_row[value]
    selected = value
    redirect['/trade/`value.id`']
```

Table options:
- `cols` — list of column keys or config objects with `key`, `label`
- `sort` — handler called when a column header is clicked (receives column name)
- `row_click` — handler called when a row is clicked (receives row data)
- `class` — CSS class for the table element

### WebSocket Lifecycle

Connection drops happen. The framework handles reconnection automatically.

```
Browser                              Server
  |                                      |
  |  ← WebSocket connected          ←  | state created in memory
  |                                      |
  |  ... user interacts ...              |
  |                                      |
  |  ✕ connection lost                   | state kept for 30s (grace period)
  |                                      |
  |  → reconnect attempt #1         →  | session cookie matches → state restored
  |  ← full HTML (re-rendered)       ←  | continue from where user left off
  |                                      |
  |  ✕ connection lost > 30s             | state destroyed
  |  → reconnect attempt             →  | no matching session → fresh state
  |  ← full HTML (fresh render)      ←  | start from scratch
```

The client-side JS runtime handles reconnection automatically:
- Exponential backoff (1s, 2s, 4s, 8s, max 30s)
- Visual indicator: `div.connection-lost` element appears when disconnected
- On reconnect, the server re-renders and sends the full HTML

Configuration:
```
secret[key]
--- state is kept for 30 seconds after disconnect (default: 30000ms)
```

### Accessibility

*Audited (2026-09-29): the runtime names fields, makes clicks pressable from the keyboard, holds focus in a dialog and returns it, announces toasts and names charts; `aria_*` attributes pass through as written (spec, Accessibility).*

HTML accessibility attributes are passed as regular attributes. The framework generates semantic HTML by default.

```
--- ARIA attributes
menu = false
fn toggle_menu[]
    menu = not menu

button['☰', click = toggle_menu, aria_expanded = menu, aria_label = 'Toggle menu']

error = ''
div[role = 'alert', class = 'error', error]

nav[aria_label = 'Main navigation',
    a['Home', href = '/'],
    a['About', href = '/about']
]

--- form accessibility
label[for = 'email', 'Email']

--- live regions (auto-announced by screen readers)

div[aria_live = 'polite', class = 'status', status_message]
```

Attribute naming: ARIA attributes use underscores instead of hyphens (`aria_label` not `aria-label`). The framework converts to hyphens in the rendered HTML.

Semantic HTML: Element functions like `nav`, `main`, `header`, `footer`, `section`, `aside` generate the corresponding semantic HTML elements — no extra attributes needed.

Keyboard navigation: All interactive elements (`button`, `ui.input`, `select`, `a`) are keyboard-accessible by default (focusable, activatable with Enter/Space). Custom keyboard handlers via `keydown` (see Keyboard Events above).

## Error Boundaries

When a handler crashes mid-render (bad query, nil access, division by zero), the framework needs a defined behavior — not a blank page or a cryptic 500.

**Default behavior:** The runtime catches the error, keeps the last successfully rendered HTML on screen, and overlays an error banner:

```
Browser shows:
┌──────────────────────────────────────────┐
│ ⚠ Error: nil access on trades.0          │
│   at app.co:47 in live handler '/'     │
│   [Dismiss]                              │
├──────────────────────────────────────────┤
│                                          │
│   (last successful render stays visible) │
│                                          │
└──────────────────────────────────────────┘
```

The error banner is only shown in development (`crow dev`). In production (`crow build`), the user sees the last good render with no error details exposed.

**Custom error handling:** Override the default with an `error_render` function:

```
view error_page_render[]
    return div[
        h1['Something went wrong'],
        p['Please try refreshing the page.'],
        button['Refresh', click = do_refresh],
        class = 'error-page'
    ]

page['/', render, on_error = error_page_render]
```

**Error in event handlers:** If a click/input handler crashes, the error is caught, the reactive variables are not mutated, and the error is available via the `error` variable:

```
error = ''
data = frame[]

fn load[]
    --- this might crash
    data = query[db, 'SELECT * FROM missing_table']

view render[]
    return div[
        button['Load', click = load],
        if len[error] gt 0
            p[error, class = 'error'],
        if len[data] gt 0
            table[data]
    ]

page['/', render]
```

The runtime automatically sets the `error` variable when an event handler throws. The next re-render shows the error. The developer can clear it: `error = ''`.

## Theming and Dark Mode

Theming is CSS-driven. The framework provides a `theme` reactive variable and a `data-theme` attribute on the root element.

```
theme = 'dark'

fn toggle_theme[]
    if theme eq 'dark'
        theme = 'light'
    else
        theme = 'dark'

view render[]
    return div[data_theme = theme, class = 'app',
        button['Toggle Theme', click = toggle_theme],
        h1['Dashboard']
    ]

page['/', render]
```

The CSS file uses `data-theme` to switch styles:

```css
[data-theme="dark"] {
  --bg: #1a1a2e;
  --text: #e0e0e0;
  --card-bg: #16213e;
  --border: #2a2a4a;
}

[data-theme="light"] {
  --bg: #ffffff;
  --text: #1a1a1a;
  --card-bg: #f5f5f5;
  --border: #e0e0e0;
}

body {
  background: var(--bg);
  color: var(--text);
}

.card {
  background: var(--card-bg);
  border: 1px solid var(--border);
}
```

For persistent theme preference, store in the session:

```
fn toggle_theme[]
    if theme eq 'dark'
        theme = 'light'
        session.set['theme', 'light']
    else
        theme = 'dark'
        session.set['theme', 'dark']

--- on page load, restore from session
fn theme_init[params]
    saved = session.get['theme']
    if saved
        theme = saved
```

No special theming API. CSS variables + state + session. The developer controls everything.

## Hooks — Client-Side Interactivity Bridge

Some interactions cannot round-trip to the server: 60fps crosshair, zoom, pan, drag-and-drop. The **hook** mechanism bridges server-managed data to a client-side JS widget.

`chart.live` is the first hook. The pattern generalizes to any client-side widget:

```
--- chart.live is a hook: server data → client-side chart engine
chart.live[ohlcv, height = 400]

--- future hooks could include:
--- map.live[locations]         — interactive map
--- editor.live[content]        — rich text editor
--- canvas.live[shapes]         — drawing canvas
```

**Hook contract:**
1. Server serializes data as JSON and embeds it in a `data-hook` div
2. Client JS runtime detects the hook element on mount
3. Client initializes the widget with the data
4. On server re-render, client receives data diffs and updates the widget incrementally (no re-creation)
5. Visual-only interactions (zoom, pan, hover) stay client-side
6. Semantic interactions (click to select, range to analyze) send events back to the server via WebSocket

Hooks are **not** escape hatches for arbitrary JS. They are purpose-built widgets bundled with Crow packages. The developer never writes JS.

## Multi-Tab Behavior

When the same user opens multiple browser tabs, each tab opens a separate WebSocket connection with its own reactive variable state.

```
Tab 1: WebSocket #1 → reactive state A
Tab 2: WebSocket #2 → reactive state B
```

**Default behavior:** Tabs are independent. Clicking a button in Tab 1 does not affect Tab 2. Each tab has its own reactive variables.

**Shared state via session:** If both tabs need to see the same data, use the session (shared across tabs via cookie) or the database:

```
positions = poll['/api/positions', 5]
selected_row = nil

--- session is shared across tabs
theme = session.get['theme', 'dark']

view render[]
    return div[table[positions]]

page['/', render]
```

**Cross-tab sync:** For real-time sync between tabs (e.g., changing symbol in Tab 1 updates Tab 2), use `channel`:

```
symbol = 'AAPL'
channel.join['dashboard']

fn on_symbol_change[]
    channel.broadcast['dashboard', [symbol = symbol]]

fn on_channel[msg]
    symbol = msg.symbol

view render[]
    return div[
        select[['AAPL', 'GOOG', 'TSLA'], symbol]
    ]

page['/', render, on_channel = on_channel]
```

`channel` is the building block for both multi-tab sync and multi-user presence (see Future Features).

## Server Push

*Rejected (2026-09-29): a write already reaches every reader, and a process outside the program is seen through `fresh` (spec, Design Note "no channels").*

`interval` polls on a timer. But sometimes an external process needs to push an update immediately — a trade execution engine fills an order, a background job completes, a price alert triggers.

### `channel.send` — push from any Crow process

```
--- in the page: subscribe to updates
user_id = 0
positions = frame[]
channel.join['trades:`user_id`']

fn on_channel[msg]
    if msg.type eq 'trade_filled'
        positions = query[db, 'SELECT * FROM positions WHERE user_id = `user_id`']
        flash['Order filled: `msg.symbol` x `msg.qty`', 5000]

view dash_render[]
    return table[positions]

page['/dashboard', dash_render, on_channel = on_channel]

--- in the trade execution engine (separate process or route):
fn execute_api[req]
    result = execute_trade[req.body]
    --- push update to the user's dashboard
    channel.send['trades:`req.body.user_id`', [
        type = 'trade_filled',
        symbol = req.body.symbol,
        qty = req.body.qty
    ]]
    return json[result]

route['/api/execute', execute_api]
```

### How channels work

```
Browser (Tab 1)                    Server                         Background Process
  |                                  |                                  |
  |  ← WS connected             ←  | state created                    |
  |  channel.join 'trades:42'       | register connection on channel   |
  |                                  |                                  |
  |                                  |  ← channel.send 'trades:42' ←  | trade filled
  |                                  |                                  |
  |                                  | find all connections on channel  |
  |                                  | run on_channel handler           |
  |                                  | state mutated, re-render         |
  |  ← HTML diff               ←  |                                  |
```

Channel API:
- `channel.join[name]` — subscribe this connection to a named channel
- `channel.leave[name]` — unsubscribe from a channel
- `channel.broadcast[name, message]` — send to all connections on the channel (including self)
- `channel.send[name, message]` — send to all connections on the channel (from outside a live handler)
- `on_channel = handler_fn` — named handler called when a message arrives on any joined channel

Channels are in-memory. If the server restarts, all subscriptions are lost (clients reconnect and re-join automatically).

## UI Testing — `live.test`

### Why no browser needed

Since `web.live` handlers run entirely on the server, UI testing is just function calls:
- The render function produces HTML from reactive variables
- Event handlers are functions that mutate reactive variables
- Re-render is calling the render function again

No Chrome, no Playwright, no Selenium, no flaky waits. Tests run at unit test speed.

### The `live.test` API

`live.test[app, path]` mounts a route, runs the initial render, and returns a test page object.

```
test 'counter starts at zero'
  page = live.test[app, '/']
  assert page.state.count eq 0
  assert 'Count: 0' in 'h1'

test 'clicking + increments'
  page = live.test[app, '/']
  page.click['button', '+']
  assert page.state.count eq 1
  assert 'Count: 1' in 'h1'
```

### Page object methods

**Actions** — find element, invoke its handler, re-render:
- `page.click[selector, text]` — invoke click handler on matching element
- `page.type[selector, value]` — invoke input handler with value
- `page.select[selector, value]` — invoke change handler with value
- `page.submit[selector]` — invoke form submit handler

**Queries** — inspect rendered HTML:
- `text in selector` — true if element with matching text exists
- `page.count[selector]` — count matching elements
- `page.text[selector]` — get text content of first matching element
- `page.attr[selector, name]` — get attribute value of first matching element

**State** — direct access to reactive variables:
- `page.state` — proxy for the reactive variables (for assertions and pre-seeding)
- `page.path` — current route path
- `page.html` — raw rendered HTML string (for debugging)

Selectors use CSS-style syntax: `'button'`, `'div.card'`, `'input[type=email]'`, `'th'`, `'p.error'`.

### Mock data

Tests should not hit real databases or APIs. Seed reactive variables via `page.state` before interacting:

```
test 'dashboard shows positions'
  page = live.test[app, '/']

  --- seed mock data
  page.state.symbol = 'AAPL'
  page.state.ohlcv = [
    [time = 1000, open = 150, high = 155, low = 149, close = 153, volume = 1000],
    [time = 1001, open = 153, high = 158, low = 152, close = 157, volume = 1200]
  ]
  page.state.positions = [
    [symbol = 'AAPL', qty = 100, entry = 150, pnl = 300],
    [symbol = 'AAPL', qty = 50, entry = 155, pnl = -100]
  ]
  page.render[]

  assert page.count['div.card'] eq 4
  assert 'AAPL' in 'div.card'
  assert '200' in 'div.card'
```

`page.render[]` re-runs the render function with the current reactive variables, producing fresh HTML. Use it after seeding state to see the result.

For handlers that call `query` or `connect`, pass mock connections:

```
test 'positions page with mock db'
  mock_conn = mock.db[[
    ['SELECT * FROM positions', [
      [symbol = 'AAPL', qty = 100, entry = 150, pnl = 300]
    ]]
  ]]

  page = live.test[app, '/positions', conn = mock_conn]
  assert page.count['tr'] eq 1
  assert 'AAPL' in 'td'
```

`mock.db` takes a list of `[query_pattern, result]` pairs. When the handler calls `query[conn, ...]`, the mock returns the matching result.

### Testing `chart.live` (hooks)

`chart.live` renders client-side — the canvas interactions (zoom, pan, crosshair) cannot be tested without a browser. But the **data contract** can be fully tested: verify that the correct data, indicators, overlays, and markers are serialized for the client.

```
test 'chart receives correct data'
  page = live.test[app, '/']
  page.state.ohlcv = [
    [time = 1000, open = 150, high = 155, low = 149, close = 153, volume = 1000]
  ]
  page.state.trades = [
    [timestamp = 1000, price = 150, side = 'buy', pnl = 50]
  ]
  page.render[]

  --- verify chart.live element exists with correct data
  assert page.has['chart.live']
  chart = page.hook['chart.live']
  assert len[chart.data] eq 1
  assert chart.data.0.close eq 153
  assert chart.indicators eq ['volume', 'macd_band']
  assert len[chart.markers] eq 1
  assert chart.markers.0.type eq 'buy'

test 'chart overlay updates on state change'
  page = live.test[app, '/']
  page.state.support = 148.50
  page.render[]

  chart = page.hook['chart.live']
  assert len[chart.overlays] eq 1
  assert chart.overlays.0.price eq 148.50
  assert chart.overlays.0.color eq '#16a34a'
```

`page.hook[name]` returns the serialized data for a hook element, allowing assertions on:
- `chart.data` — the OHLCV data passed to the chart
- `chart.indicators` — list of indicator names
- `chart.overlays` — list of overlay configs
- `chart.markers` — list of marker configs

This tests everything Crow controls (data, config, layout). The client-side rendering (Canvas, interactions) is the chart engine's responsibility and is tested separately in the engine's own test suite.

### What `live.test` covers vs. what it doesn't

| Covered (no browser needed) | Not covered (needs browser/renderer) |
|---|---|
| Handler logic and state mutations | CSS visual rendering and layout |
| Event handler invocation | Canvas/WebGL chart rendering |
| Conditional rendering (`if`/`else`) | Zoom, pan, crosshair interactions |
| List rendering (`for` loops) | Browser-specific behavior (scroll, focus) |
| HTML structure and content | Animation and transitions |
| Form validation | Network latency effects |
| Mock data and DB queries | WebSocket reconnection |
| Hook data serialization | Client-side hook widget behavior |
| Navigation between routes | Browser history (back/forward) |
| CSS class/style assertions | Whether CSS actually looks correct |

The "not covered" column is addressed by `crow dev` (manual visual inspection) and `live.screenshot` (automated visual regression) below.

## Visual Testing

### Three levels of CSS/visual verification

| Level | Tool | What it catches | Speed |
|---|---|---|---|
| 1. Class assertions | `live.test` | Wrong class, missing style attribute | Instant (no browser) |
| 2. Live preview | `crow dev` | Visual bugs during development | Manual (human eyes) |
| 3. Screenshot regression | `live.screenshot` | Visual regressions between changes | Automated (needs renderer) |

### Level 1: Class and style assertions (in `live.test`)

Already available — verify that the right CSS classes and styles are applied to elements:

```
test 'card has correct styling'
  page = live.test[app, '/']
  assert page.attr['div.card', 'class'] eq 'card'
  assert page.has['div.stats']
  assert page.count['div.card'] eq 4

test 'error state adds error class'
  page = live.test[app, '/login']
  page.submit['form']
  assert page.has['p.error']
  assert page.attr['p.error', 'class'] contains 'error'
```

This catches structural bugs ("forgot to add the class") but not visual bugs ("the class looks wrong").

### Level 2: `crow dev` — live preview with hot reload

During development, `crow dev` serves the app with automatic hot reload on file save:

```
crow dev app.co
--- Server running at http://localhost:8080
--- Watching app.co for changes
--- Hot reload enabled
```

Features:
- Opens the app in the default browser
- Watches `.co` and `.css` files for changes
- On save: re-compiles, re-renders, pushes diff to browser (no manual refresh)
- Shows all `live` routes — navigate between them to inspect visually
- Error overlay: if the Crow file has errors, shows them in the browser instead of crashing

This is the primary tool for CSS iteration. Edit CSS, save, see the result instantly.

### Level 3: `live.screenshot` — automated visual regression

Captures rendered pages as screenshots and compares against reference images. Catches visual regressions automatically.

```
test 'dashboard looks correct'
  page = live.test[app, '/']
  page.state.symbol = 'AAPL'
  page.state.positions = [
    [symbol = 'AAPL', qty = 100, entry = 150, pnl = 300],
    [symbol = 'GOOG', qty = 50, entry = 2800, pnl = -100]
  ]
  page.render[]
  page.screenshot['dashboard']

test 'login form error state'
  page = live.test[app, '/login']
  page.submit['form']
  page.screenshot['login-error']

test 'empty state'
  page = live.test[app, '/']
  page.state.positions = []
  page.render[]
  page.screenshot['dashboard-empty']
```

**Workflow:**

```
1. Write test with page.screenshot['name']

2. First run:  crow test
   → No reference exists
   → Renders page to image
   → Saves to snapshots/name.png
   → Test passes (baseline created)

3. Develop normally, change CSS or layout

4. Run again:  crow test
   → Renders page to image
   → Pixel-diff against snapshots/name.png
   → If diff < threshold (default 0.1%) → pass
   → If diff > threshold → FAIL, saves diff image to snapshots/name.diff.png

5. If the change was intentional:
   crow snapshot update
   → Replaces all reference images with current renders
   → Next run passes

6. If the change was a bug:
   → Fix the CSS
   → Run again → passes
```

**Screenshot options:**

```
--- custom viewport size
page.screenshot['dashboard', width = 1280, height = 720]

--- mobile viewport
page.screenshot['dashboard-mobile', width = 375, height = 667]

--- capture a specific element, not the full page
page.screenshot['nav-bar', selector = 'header.main-header']

--- custom diff threshold (percentage of pixels that can differ)
page.screenshot['dashboard', threshold = 0.5]

--- dark mode
page.screenshot['dashboard-dark', color_scheme = 'dark']
```

**How it renders:**

`live.screenshot` uses the OS-native WebView to render HTML to an image:
- macOS: `WKWebView`
- Linux: `WebKitGTK`
- Windows: `WebView2`

No Chromium download, no Playwright install, no external dependencies. The WebView is already on the machine. Crow's test runner spins up a hidden WebView, loads the rendered HTML + CSS, captures the bitmap, and compares.

Since Crow already produces complete HTML on the server, the WebView just needs to paint it — no navigation, no JavaScript execution, no network requests.

## Future Features (Nice-to-Have)

These features are not required for the initial release but are documented here for future consideration.

### Multi-User Presence

Show who else is viewing the same page. Built on top of `channel`:

```
channel.join['presence:dashboard']
viewers = channel.presence['presence:dashboard']

view render[]
    return div[
        for v in viewers
            span[v.name, class = 'avatar'],
        class = 'viewers'
    ]

page['/dashboard', render]
```

`channel.presence[name]` returns a list of all users currently subscribed to the channel. The framework automatically tracks join/leave events. Useful for collaborative editing, shared dashboards, and chat rooms.

**Complexity:** High — requires presence tracking, heartbeats, and cleanup on disconnect.

### Drag and Drop

Reorder lists, move items between columns (Kanban boards). Implemented as a hook (like `chart.live`) because drag interactions are 60fps client-side:

```
columns = [
    [name = 'Todo', items = ['Task 1', 'Task 2']],
    [name = 'Done', items = ['Task 3']]
]

fn on_hook[event]
    if event.hook eq 'drag.sortable' and event.type eq 'reorder'
        columns = reorder[columns, event.from, event.to]

view render[]
    return div[
        for col in columns
            div[class = 'column', hook = 'drag.sortable', data_column = col.name,
                h3[col.name],
                for item in col.items
                    div[item, class = 'card']
            ],
        class = 'kanban'
    ]

page['/board', render, on_hook = on_hook]
```

The `drag.sortable` hook handles the visual drag interaction client-side and sends the final position to the server via `on_hook`.

**Complexity:** High — requires a client-side drag library (or custom implementation) and a hook contract.

### Animations and Transitions

CSS-only animations work today (add/remove classes, CSS `transition` property). Framework-level animation support would add:

```
--- element enter/exit animations
div[animate = 'fade', class = 'card']
  p['This fades in when added, fades out when removed']

--- page transitions
page['/', render, transition = 'slide']
```

The `animate` attribute tells the JS runtime to add CSS classes (`animate-enter`, `animate-exit`) when elements are added/removed from the DOM. The `transition` option on `page` adds page-level transition classes during navigation.

**Complexity:** Medium — requires the JS runtime to detect element add/remove and apply CSS classes with timing.

### Client-Side Validation

Instant feedback without server round-trip. Currently, debounce + server validation covers most cases. Dedicated client-side validation would add:

```
ui.input[type = 'email', validate = 'email']
ui.input[type = 'text', validate = 'min_length:3']
ui.input[type = 'number', min = 0, max = 100]
```

The `validate` attribute runs a check in the JS runtime before sending the event to the server. If validation fails, a CSS class (`invalid`) is added and the event is not sent.

**Complexity:** Low — but adds logic to the JS runtime that duplicates server-side validation. Risk of divergence.

### Internationalization (i18n)

Translation support. Can be done with plain Crow functions today:

```
fn t[key]
  translations = [
    'welcome' = 'Welcome'
    'logout' = 'Log out'
  ]
  translations[key] or key

h1[t['welcome']]
button[click = logout, t['logout']]
```

A dedicated i18n module would add locale detection, pluralization, and date/number formatting:

```
i18n.locale['en']
h1[i18n.t['welcome']]
p[i18n.n[1500.50]]  --- formats as "1,500.50" or "1.500,50" depending on locale
p[i18n.d[now[]]]     --- formats date per locale
```

**Complexity:** Medium — the translation lookup is simple, but pluralization rules and locale-aware formatting are non-trivial.

### Lazy Loading and Infinite Scroll

Load content on demand as the user scrolls. Built on a hook for scroll detection:

```
items = frame[]
pg = 1

fn load_page[]
    items = query[db, 'SELECT * FROM posts LIMIT 20 OFFSET `[pg - 1] * 20`']

fn on_hook[event]
    if event.hook eq 'scroll.bottom'
        pg = pg + 1
        new_items = query[db, 'SELECT * FROM posts LIMIT 20 OFFSET `[pg - 1] * 20`']
        items = items + new_items

view render[]
    return div[
        for item in items
            div[item.title, class = 'post'],
        div[hook = 'scroll.bottom', data_threshold = 100],
        class = 'feed'
    ]

page['/feed', render, on_hook = on_hook]
```

The `scroll.bottom` hook fires a client-side event when the element enters the viewport. The server appends more items to the list.

**Complexity:** Low-Medium — the hook is simple, but managing growing state and avoiding duplicate loads needs care.

## Full Example — Trading Dashboard

```
use web, ui, frame

--- data sources (reactive)
playbooks = fetch['/api/playbooks']
positions = poll['/api/positions', 5]
trades = poll['/api/trades', 5]

--- filters (two-way bound)
struct Filters [min_vol, max_vol, min_price, max_price, filter_pb]
f = Filters[0, 999999, 0, 999999, 'all']

--- data operations
fn apply_filters[data, f]
    result = data[data.volume >= f.min_vol and data.volume <= f.max_vol]
    result = result[result.price >= f.min_price and result.price <= f.max_price]
    if f.filter_pb not eq 'all'
        result = result[result.playbook_code eq f.filter_pb]
    result

fn scanner[data]
    filtered = apply_filters[data, f]
    sorted = sort[filtered, volume, desc]
    table[sorted]

fn performance[trades]
    today_trades = trades[trades.date eq fmt[now[], style = 'date']]
    summary = group[today_trades, playbook_code, [pnl, sum], [pnl, count], [pnl, mean]]
    summary = sort[summary, pnl_sum, desc]
    table[summary]

--- render function
view render[]
    div[
        h1['Trading Dashboard'],
        div[
            field['Min Vol', f.min_vol],
            field['Max Vol', f.max_vol],
            field['Min $', f.min_price],
            field['Max $', f.max_price],
            select[unique[positions.playbook_code], f.filter_pb],
            class = 'filters'
        ],
        div[
            div[
                h2['Scanner (`len[apply_filters[positions, f]]` results)'],
                scanner[positions],
                class = 'scanner'
            ],
            div[
                h2['Open Positions (`len[positions]`)'],
                table[positions],
                class = 'positions'
            ],
            div[
                h2['Recent Trades'],
                table[head[trades, 20]],
                class = 'trades'
            ],
            div[
                h2['Performance'],
                performance[trades],
                class = 'performance'
            ],
            class = 'grid'
        ],
        class = 'dashboard'
    ]

serve[3000]
page['/', render]
```

65 lines. Real-time polling, filtered scanner, grouped performance, sortable tables.
