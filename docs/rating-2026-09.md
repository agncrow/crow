# Rating — September 2026

Where Crow stands against the best comparator on each dimension, written
after the finch simulation page was rebuilt as parts on `derive` and the
verification design (`app-baseline-design.md`) was agreed. Scores are
out of 10 and are a judgment, not a measurement. Each row is a
workstream; revisit the table when one moves.

## The table

| Dimension | Crow today | If the baseline design ships | Best in class, and why |
|---|---|---|---|
| Language model: explicit state, effects, controls; one way; two modes | 8 | 8 | Elm 8, Rust 8. Crow's model is as principled as Elm's and covers data and UI in one language. Weaker on declared types |
| Verification without tests | 6 | 9 | Rust 8 for memory and types, Elm 7, hardware equivalence checking 9. Nothing in application languages matches derived behaviour diffs |
| UI framework: layout engine in the compiler, kernel look, harness | 7 | 8 | React 9 for breadth, SwiftUI 8 for layout. Crow's vocabulary is small and client-side interaction is thin |
| Data: frames, typed query cells, three backends | 6 | 6 | Polars and pandas 9. Crow's ergonomics are good; the surface is a fraction of theirs |
| Math and ML | 5 | 5 | PyTorch 10, Julia 8. Tensors, autograd and a small nn module; nowhere near |
| Performance | 6 | 6 | Rust 10, Julia 8. Compiles to Rust with parallel loops; unproven under load |
| Tooling: check, test, book, lsp, fmt in one binary | 6 | 8 | Rust 9, Go 9. Coherent and young |
| Documentation | 8 | 8 | Rust 9. A book verified in both modes at this age is unusual |
| Ecosystem, community, hiring | 1 | 1 | TypeScript 10, Python 10. One developer, proprietary, no packages, no users |

## Where it leads

Three things are ahead of the field, and the baseline design turns two
of them into a category: a model where writers, readers, controls and
effects are explicit; two execution modes held to identical behaviour by
suites, which is what makes "what was checked is what ships" true; and a
layout engine that lives in the compiler rather than the browser. With
derived behaviour diffs, Crow would be the only application language
where a change tells you what else it changed without anyone writing a
test or a rule. Elm came closest and stopped at types.

## Where it lags

The ecosystem row dominates any practical rating. A language with one
author, no package registry and no external users is a research vehicle
however good the model, and that row moves by years and other people,
not by design work. Data and ML are a fraction of Python's world,
performance is plausible but unproven, and the UI vocabulary needs to
grow several times over before a product team stops reaching for the
escape hatch.

## The overall

As a language design: top tier for coherence, with Elm and Unison as
peers and a broader remit than either. As a product for our own apps:
already productive, as finch shows, with the compile time and the
browser gap as the daily costs. As something a team could adopt today:
not yet, for the reasons in the last row.

## What moves the numbers, in order

1. Ship the derived behaviour diff and keep it quiet enough to trust.
2. A second app built by someone other than us — the only test of the
   model's generality.
3. Time in production for the compiled runtime.

## Prior art for the verification design, by family

| Family | Examples | What they give | Where Crow's design differs |
|---|---|---|---|
| Types as the "what else broke" signal | Elm, Rust, TypeScript, Haskell | Change a signature and every caller fails to compile; Elm forces every message to be handled | Reach for type-level changes only; a guard flipped from `lte` to `lt` compiles everywhere. The design is the same idea at the behaviour level |
| Approval and snapshot testing | ApprovalTests, insta, Verify, Jest snapshots | The accept-baseline workflow: record, approve, diff | The test that produces the artifact is hand-written and the artifact is output text, so refactors churn it. Crow derives a canonical artifact, so only behaviour moves it |
| Derived semantic diffs | Django and Prisma migrations, cargo-semver-checks, Go apidiff, Revapi | A diff of meaning derived from code with no rules: schema changes, breaking API changes | Proven workflow, narrow subject. Those diff a schema or a public surface; this diffs what controls do in every state |
| Differential verification | SymDiff, regression verification tools, shadow symbolic execution | Prove two versions equivalent or show the input that separates them | Research-grade on ordinary code because effects hide, state aliases and loops are everywhere. Crow's handlers are small and effect-explicit |
| Equivalence checking in hardware | Cadence Conformal, Synopsys Formality | The industry that stopped writing tests for changes: prove the new netlist matches the old | The strongest precedent. Software never had the model; chip design did |
| Rules over a code graph | CodeQL, Semgrep, Infer | Findings from a derived graph on every change | Their power is hand-written queries — the rule maintenance the design rejects. Only Infer's built-in checkers work like Crow's kernel rules |
| Reactive runtimes with a dependency graph | Svelte, Solid, Vue, MobX, Convex | The graph exists inside the runtime | Never exposed, never diffed, never checked |
| Whole-app previews and stories | SwiftUI previews, Storybook, Chromatic | Rendered components, pixel regression | Authored stories and pixel diffs reviewed by eye; Crow derives the pages and diffs structure with attribution |

Every family has one of the three things the design needs — an explicit
graph of who writes and reads state, effects as values, controls
declared in the view — and none has all three. Crow has all three for
reasons unrelated to verification (parallelism, parity), and this is
the dividend.
